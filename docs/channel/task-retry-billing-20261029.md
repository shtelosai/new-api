# 2026-10-29 任务重试预扣、退款与扣费核对

## 来源与去重

基于公司 `main` 的 `93c7eca44`，适配 [55e2ae54d](https://github.com/QuantumNous/new-api/commit/55e2ae54d1445d92482ac9bb27b2409bb8f46b70) 的任务重试提交前补扣行为。

核对发现，公司原生任务每次尝试已经调用 `ModelPriceHelperPerCall`，分组与渠道倍率已有计算；已有 `BillingSession.Reserve` 的钱包退款累计也已正确使用 `+=`。这些行为保留，不重复替换。公司没有上游新版 JS 任务插件计价体系，本次不新增插件或插件表达式定价功能，也不迁入只适用于该体系的表达式快照重定价代码。

缺失部分为：已有计费会话时任务提交跳过预扣；`PreConsumeBilling` 再调用会新建会话而非补足差额。现在重试复用原会话，按当前尝试价格在提交前补足差额。更便宜或免费的尝试不提前释放预留，在最终结算时一次退回差额。

## 公司余额路径适配

- 新增 `ReserveBeforeSubmit`，与允许按实际用量补账的原 `Reserve` 分开；不修改原有后结算规则。钱包、令牌或订阅不足时不调用更贵上游。
- 上游原子预留模块依赖新版缓存结构，公司分支使用独立的任务重试事务：在现有图片额度桥屏障下等待批量写入完成，将该用户和令牌尚未落库的额度增量纳入同一事务，再做带余额条件的扣减。失败时事务回滚、队列不丢；成功后清理已提交增量，避免批处理再扣一次。
- 钱包或订阅与令牌在同一事务预留；订阅沿用原订阅 ID，令牌预留失败时事务一并回滚订阅差额。不会在重试时更换资金来源或新建计费会话。
- 缓存余额不作为提交前的最终余额凭据；成功提交后失效相关缓存，缓存操作在计费锁释放后执行。没有把新交易路径推广到所有普通聊天预扣。
- 网关自己的预扣失败标记为本地错误，不按上游渠道故障记录。
- 回归额外发现两个相关缺口并补齐：退款后的迟到 Settle 不得再扣费；订阅预扣退款原先在记录事务中另开连接更新余额，单连接库会卡住，且记录与余额不原子。现在复用同一事务更新订阅余额与退款记录，保留共用行锁与三种数据库的 GORM 路径。

## 隔离库扣费核对

以下为固定测试数据的 quota，对应钱包/令牌数据库回读，不代表生产价格或供应商账单。

真实本地 HTTP 使用两条原生视频渠道：基础单价 0.00005、QuotaPerUnit=500000、分组倍率 1、时长 4。首次渠道倍率 1：`0.00005 × 500000 × 1 × 4 = 100`；重试渠道倍率 3：300；较便宜渠道倍率 0.4：40。均使用整值结果，避免把既有按次整数截断规则混入本次验证。

| 场景 | 初始钱包 / 令牌 | 首次预扣 | 重试提交前追加 | 最终净扣 | 最终钱包 / 令牌 |
| --- | --- | ---: | ---: | ---: | --- |
| 更贵渠道成功 | 1000 / 1000 | 100 | 200 | 300 | 700 / 700 |
| 更便宜渠道成功 | 1000 / 1000 | 100 | 0 | 40（退回 60） | 960 / 960 |
| 钱包不足 | 200 / 1000 | 100 | 拒绝，未调用重试上游 | 0 | 200 / 1000 |
| 令牌不足 | 1000 / 200 | 100 | 原子失败，钱包补扣回滚；未调用重试上游 | 0 | 1000 / 200 |
| 两个上游都失败 | 1000 / 1000 | 100 | 200 | 0（退回全部 300） | 1000 / 1000 |

成功案例核对：上游调用时已经预留足够额度、实际映射模型、最终余额、token.used_quota、user.used_quota、单条消费日志、单条任务记录和最终渠道倍率快照。失败案例核对无任务/消费日志、无多余上游调用、全部预扣退还。

服务层另验证更便宜目标 50、免费目标 0、重复预留、重复结算/退款和退款后迟到结算。订阅路径分别验证 100 → 300 成功、订阅额度不足、令牌不足时订阅补偿、全部失败退回 300；成功时订阅 used=300、令牌 used=300，失败时均回到 0，钱包始终不变。重复处理订阅预扣退款回执不再退费。
